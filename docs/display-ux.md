# Display and customization decisions

Updated October 23, 2026 from Emma's design feedback. These decisions supersede the initial
all-sounds dropdown layout. See [team notes](../TEAM-NOTES.md) for the running context.

## Defaults, then exceptions

Start with Less interruption / Balanced / More awareness. Let people search for a sound and add
only the rules they want to change. The short exception list is not the backend's notification queue.
Removing a rule restores its preset; switching presets preserves explicit overrides, including tier 0.
Keep optional name setup optional. Appearance belongs in a collapsed section with an immediate preview.

“Fully customizable” describes preference control, not unlimited recognition. The searchable catalog
must mark supported detection, planned name detection, and mock-only sounds accurately. Niche sound
requests need model coverage/evaluation or a future enrollment workflow; typing a sound name cannot
make it detectable. Do not dump all classifier labels into onboarding without validating them.

Current local preferences are a browser simulator, not persisted live settings. Backend profile
integration remains a TODO. Keep appearance fields separate from the proposed core profile JSON
until that schema is agreed. `event_tiers` remains numeric 0–4 and contains explicit overrides only.

## Peripheral icon cues

Desired experience: a small icon at the edge nearest the sound's direction, inspired by a game
sound-visualization overlay. Ordinary events are icon-first by default; labels remain optional for
learning or ambiguous icons. Urgent cues include a short label. Do not assume icons are understood
without a wearer comprehension test. Retain an accessible event description and the readable browser log.

Implemented browser design preview: left/right/front/behind placements, user-selectable tier colors,
optional labels, and still or gentle two-cycle scale pulse. Direction positions are **simulated** and
labeled. Front maps to top and behind to bottom for this concept, not a validated wearer coordinate
system. Receiver mode ignores this simulated direction and remains unknown. No localization API
or real-world arrows are enabled by these controls.

Color alone must never identify urgency: icon, border, label and duration still carry information.
The SSD1306 is white monochrome; browser colors do not become physical OLED colors. The offline
[device renderer](display-renderer.md) has separate static tier treatments; browser/device icon parity
and final visual mappings still need integration.

Motion defaults off. The optional pulse scales gently twice, then stops; there is no blinking or
rapid luminance flashing. Honor reduced-motion settings. This follows the intent of W3C's
[flash guidance](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
and [interaction-animation guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html).
These references do not establish headset safety or WCAG conformance for this prototype.

## What the OLED can and cannot establish

128×64 describes the panel's pixels, not its angular field of view through optics. One fixed OLED
may occupy a small region of vision. Moving an icon to its leftmost pixel does not necessarily put
that icon at the left edge of the wearer's whole field of view. A full-field overlay depends on the
optical system, placement and calibration, which are not provided by the display specification alone.

Ask Yameen to confirm:

- Where does the virtual image appear relative to forward gaze, and in which eye?
- What angular field of view, focus distance, eye relief and usable eye box do the optics provide?
- Is the image mirrored or rotated? Which pixels correspond to wearer-left/right?
- Can the display show peripheral positions across the desired field, or only within one small panel?
- What are the refresh and brightness limits, and is a readable icon possible without obscuring vision?

If the image is a small fixed patch, use direction indication **within that patch** (once localization
is reliable) rather than promising an icon anywhere around the visual field. Two microphones also
leave directional ambiguities to resolve; mock front/behind placement does not solve those.

## Design tooling and validation

The React mirror was built locally, not generated by Mana. Mana is being used for the separate
onboarding feature; source/export readiness is tracked in the sponsor guide.

Taste's app-screen guidance was installed and applied to the cleanup: neutral chrome, plain
sentence-case labels, one primary alert area, readable type and no eyebrow headings or decorative
reticles. Chosen style: Achromatic ledger, seed 15283662, keeping the existing palette/type roles.
Its generic finance/usage patterns were not copied into a sound display. No invented metrics.

Taste source lint passes with zero failures/warnings. Browser review uses the supported computer-use
tools; Taste's separate browser-driving inspector was not run. Do not claim its three-width gate passed.
The physical OLED pixel font and native terminal/JSON blocks keep monospace because it is functional.
